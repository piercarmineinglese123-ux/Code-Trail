Finding a bug by staring at code and hoping works rarely. A strategy based on **evidence** works much better.

## Reproduce it

Find exact steps (inputs, order of actions) that trigger the bug every time. Then try to shrink them: the smallest input that still fails is the most useful clue.

## Use the scientific method

1. **Observe**: what exactly goes wrong? Compare actual and expected output.
2. **Hypothesize**: guess a specific cause ("the loop stops one iteration early").
3. **Predict**: if the guess is right, what else must be true?
4. **Test**: run an experiment (print a value, change an input) to confirm or reject it.
5. **Repeat** until the cause is clear.

A wrong hypothesis is still progress: it eliminates one possibility.

## Narrow the search

- **Divide and conquer.** Check a value halfway through the program. Is it already wrong there? Then the bug is in the first half; otherwise in the second. Repeat.
- Test functions **separately** with known inputs.
- Comment out unrelated code to see if the problem disappears.

## Rules of thumb

- Change **one thing at a time**, and undo changes that did not help.
- Do not assume. Verify what the code does rather than what you think it does.
- Make notes of what you tried so you do not repeat yourself.
- When stuck, take a break or explain the problem aloud to someone (or something); gaps in your reasoning often show up.
- When asking for help, include a short, complete example that reproduces the problem.

## Recap

- Make the bug reproducible and as small as possible.
- Form a hypothesis, test it with an experiment, and learn from the result.
- Narrow down the location by checking values at the midpoint and by testing parts separately.
- Change one thing at a time and keep notes.
